**Findings**

1. **Config and role definitions are internally inconsistent, which is likely to break auth or deployments.**  
   The docs say the backend uses `AZURE_TENANT_ID`, `BACKEND_API_CLIENT_ID`, and `BLOB_STORAGE_CONNECTION_STRING`, and that editor roles are `Author`, `Publisher`, or `Admin` ([README.md](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\README.md:126), [README.md](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\README.md:141)). The code actually reads `ENTRA_TENANT_ID`, `ENTRA_CLIENT_ID`, and `STORAGE_CONNECTION_STRING` ([storage.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\services\backend-functions\src\lib\storage.ts:7), [validateToken.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\services\backend-functions\src\middleware\validateToken.ts:15), [validateToken.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\services\backend-functions\src\middleware\validateToken.ts:37)), and the runtime role model is just `ContentEditor | Learner` ([shared/auth/src/index.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\shared\auth\src\index.ts:11), [savePage.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\services\backend-functions\src\functions\savePage.ts:47), [publish.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\services\backend-functions\src\functions\publish.ts:22)). That mismatch is more than documentation debt; it makes the security model hard to reason about and easy to misconfigure.

2. **The block rendering contract is fragmented across apps, so behavior will drift.**  
   The learner app renders blocks through the shared registry ([BlockRenderer](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-learnersite-dev\components\BlockRenderer\index.tsx:3)), but the public site has its own large hand-written renderer and switch statement ([PublicBlockRenderer](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-publicsite-dev\src\components\PublicBlockRenderer\index.tsx:13), [PublicBlockRenderer](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-publicsite-dev\src\components\PublicBlockRenderer\index.tsx:510)). At the same time, the editor registry already contains several stubbed block implementations like “Gallery”, “Audio”, “Image and text”, and “File” ([registerDefaultBlocks.tsx](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-editorsite-dev\src\blocks\registerDefaultBlocks.tsx:172), [registerDefaultBlocks.tsx](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-editorsite-dev\src\blocks\registerDefaultBlocks.tsx:182), [registerDefaultBlocks.tsx](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-editorsite-dev\src\blocks\registerDefaultBlocks.tsx:243), [registerDefaultBlocks.tsx](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-editorsite-dev\src\blocks\registerDefaultBlocks.tsx:253)). That means “add one block type” is currently a multi-app coordination problem, not a shared-platform capability.

3. **There is unsanitized HTML rendering in the authoring/display path.**  
   The shared block schema treats paragraph/detail bodies as raw HTML strings ([shared/block-registry/src/index.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\shared\block-registry\src\index.ts:75), [shared/block-registry/src/index.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\shared\block-registry\src\index.ts:96)), and both the editor preview and public renderer inject that HTML with `dangerouslySetInnerHTML` ([registerDefaultBlocks.tsx](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-editorsite-dev\src\blocks\registerDefaultBlocks.tsx:89), [registerDefaultBlocks.tsx](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-editorsite-dev\src\blocks\registerDefaultBlocks.tsx:150), [PublicBlockRenderer](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-publicsite-dev\src\components\PublicBlockRenderer\index.tsx:47), [PublicBlockRenderer](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-publicsite-dev\src\components\PublicBlockRenderer\index.tsx:79)). I didn’t find a sanitization layer in the sampled paths. If authors can paste arbitrary markup, this is a clear XSS surface.

4. **The data model is carrying two architectures at once.**  
   The schema package explicitly keeps a legacy flat course/enrolment/progress model while also introducing the newer `PATH -> MODULE -> UNIT` catalogue model ([shared/schemas/src/index.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\shared\schemas\src\index.ts:32), [shared/schemas/src/index.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\shared\schemas\src\index.ts:60), [shared/schemas/src/index.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\shared\schemas\src\index.ts:107)). The backend storage layer does the same, with old course catalogue tables and newer catalogue/path/module/unit tables side by side ([storage.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\services\backend-functions\src\lib\storage.ts:44), [storage.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\services\backend-functions\src\lib\storage.ts:866)). That is understandable mid-migration, but architecturally it increases cognitive load, raises regression risk, and makes it harder to know which model is the real source of truth.

5. **The public-site implementation doesn’t fully match the “static-first / no runtime API” goal.**  
   The project description emphasizes static-first delivery and a KB with no runtime APIs ([README.md](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\README.md:3), [about-this-project](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\about-this-project:11)), but the public site is a client-routed SPA using `BrowserRouter` ([App.tsx](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-publicsite-dev\src\App.tsx:18)) and client-side fetches for pages and nav ([usePage.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-publicsite-dev\src\hooks\usePage.ts:46), [useNav.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-publicsite-dev\src\hooks\useNav.ts:17)). That’s workable, but it gives you SPA SEO/loading tradeoffs while also retaining backend dependency for content retrieval.

6. **The backend storage patterns will get expensive and brittle as content volume grows.**  
   The storage layer does a lot of table scans/list-and-filter work and some delete-and-recreate reorder operations ([storage.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\services\backend-functions\src\lib\storage.ts:82), [storage.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\services\backend-functions\src\lib\storage.ts:866), [storage.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\services\backend-functions\src\lib\storage.ts:935)). Azure Table Storage can handle a lot, but these patterns are awkward for transactional updates, reordering, richer querying, and future reporting. It feels fine for an MVP, but it’s not a great long-term fit for a content graph with hierarchy, versioning, enrolments, and progress analytics.

7. **There’s very little visible verification infrastructure.**  
   The root workspace exposes build and lint only, with no test orchestration ([package.json](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\package.json:13)). The sampled package manifests also only expose build/lint/dev flows, and the learner app explicitly falls back to mock data when the API is absent ([apiClient.ts](C:\Users\Pauli\.codex\worktrees\35e9\lms-platform\apps\lms-learnersite-dev\lib\apiClient.ts:89)). That makes iteration easy, but it also means architecture drift, contract mismatches, and auth regressions can survive a long time without being caught automatically.

**Most valuable improvement directions**

- Unify the auth/config contract first: one env naming scheme, one role model, one source of truth in docs and code.
- Make `@lms/block-registry` the real shared rendering contract for all apps, not just the learner app.
- Introduce a sanitization boundary for authored HTML, or better, move rich text to a safer structured format.
- Pick a migration plan for the old vs new catalogue model so the codebase stops straddling both.
- Decide whether the public/KB sites are truly static or intentionally SPA-plus-API, then align implementation to that choice.
- Add a small but real test layer: schema contract tests, function integration tests, and one end-to-end publish/render path.
